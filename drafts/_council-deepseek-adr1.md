**VERDICTS & REASONING**

**1. "miniaudio via ruby-ffi with all state C-side is the right foundation for this stack"**
VERDICT: **UNCERTAIN** — The engine choice is *plausible* but hinges on unvalidated performance characteristics critical to the 16.6ms p95 tick budget. The ADR claims "p95 command cost" will be spike-tested, but this is a **lagging indicator of failure**. The architectural risk is that ruby-ffi calls for every audio command (volume changes, panning, filter updates) have non-trivial overhead, and miniaudio's C API is not designed for batched, zero-allocation command submission from an interpreted language. Each `ma_sound_set_volume` call is a full FFI transition. For a complex soundscape (64 voices, bus updates per tick), this could saturate the budget *before* spike falsification. The "200-400 lines of FFI bindings" handwaves this cost. **SoLoud's C++ API is equally susceptible.** The correct engine choice cannot be confirmed until a *performance prototype* exists, making this ADR premature.

**2. "The audio thread never enters Ruby; polling instead of callbacks is sufficient"**
VERDICT: **REFUTED** — For the stated feature "music state machine (crossfades, stems)", a poll-only model is **architecturally insufficient** or prohibitively complex. Seamless music stem transitions and crossfades often rely on sample-accurate or buffer-accurate synchronization events from the audio thread. Polling `ma_sound_at_end` for a looped stem is meaningless; you need to know *when a specific bar or beat is reached* to trigger the next stem. This requires a callback or a mechanism to query the current playback position with high precision (which miniaudio provides via `ma_sound_get_time_in_pcm_frames`), but then the *game thread* must poll at a rate high enough to catch the exact transition point (~every 10-20ms), adding non-deterministic jitter to musical timing. The ADR's blanket "polling is sufficient" ignores this core musical requirement, degrading the feature.

**3. "Offline noDevice render as the CI ship-gate, with byte-identical WAV across two runs..."**
VERDICT: **REFUTED** — Bit-exactness is **not a sound expectation** for a real-time audio engine, even in `noDevice` mode. The ADR's own caveat ("given fixed engine version + dither settings") hints at the problem, but misses the critical points:
    *   **Internal threading:** `ma_engine` uses a background thread for mixing even with `noDevice`. The order of mixing of concurrent sounds can be non-deterministic across runs due to OS thread scheduling, potentially causing differences at sample boundaries, especially with filters or dithering applied.
    *   **Floating-point non-associativity:** Parallel mixing of multiple voices can produce different rounding errors in different runs.
    *   **Resampler state:** If any sound has a playback speed other than 1.0, the resampler's internal state may be seeded differently (e.g., based on system time or RNG) or be sensitive to scheduling.
    The only way to guarantee bit-exactness is to **disable all internal threading** (not documented as possible in engine API) and **lock down all floating-point behavior** (compiler flags, `-ffloat-store`). This is a massive, unaccounted-for spike burden. The gate should be "statistically identical (e.g., RMS within epsilon)", not "byte-identical".

**4. "SDL_AUDIODRIVER=dummy before Gosu init silences Gosu audio safely"**
VERDICT: **CONFIRMED** — This is a standard and safe SDL2 pattern. Setting the environment variable before SDL_Init (which Gosu calls internally) prevents SDL from initializing any audio subsystem. Gosu graphics and input are independent modules. No failure mode beyond the obvious: if any code (e.g., a Gem) depends on SDL audio being present, it may crash or behave unexpectedly. This is not a risk for the described Gosu 1.4.6 game stack.

**5. "Vendored prebuilt miniaudio.dll in git + absolute-path ffi_lib is the right packaging"**
VERDICT: **REFUTED** — Committing a binary DLL to a git repository that will be built on **two different Windows machines** is a reproducibility hazard. The ADR assumes `gcc -shared -O2` produces an ABI-stable binary across machines. This is false. Different versions of the Mingw-w64 GCC toolchain (which MSYS2 can update independently), different Windows SDK versions, or even different `-O2` optimization behaviors in different compiler releases can produce a DLL with different internal structures, causing mysterious crashes when the Ruby-FFI bindings expect specific struct layouts or calling conventions. The correct packaging is to **document the exact MSYS2 environment (package versions)** and **compile the DLL as part of the `bundle install` process**, not to commit a binary.

**6. "Deterministic lockstep safety: audio as pure event-bus sink cannot desync the sim"**
VERDICT: **UNCERTAIN** — The ADR correctly isolates audio commands from the sim state. However, it misses a **covert feedback path**: **Garbage Collection timing.** The audio system, while using "opaque handles and preallocated command structs," will still generate Ruby objects (e.g., for parsing cue table JSON, handling event bus messages). A GC cycle triggered by audio-related allocations could delay the *subsequent* game tick's start time. In a deterministic lockstep where each peer must finish the tick within a fixed window, one peer experiencing a GC stall due to audio could fall behind, causing a network desync *indirectly*. The claim "GC.stat watched in the perf harness" is reactive, not preventative. This risk is acknowledged but its potential to violate the lockstep constraint is understated.

**FINAL: BIGGEST RISK NOT THOUGHT OF**

**The "Deterministic Offline Render" CI gate is a **single-point architectural failure** that is very likely unimplementable as described (bit-exact WAV).** When the spike inevitably fails to achieve byte-identical outputs, the team will be forced into a deep, time-consuming investigation into miniaudio's internals, compiler flags, and threading model—areas completely outside the project's domain expertise. This could waste weeks, only to settle for a fuzzy, statistical comparison gate that undermines confidence in the entire deterministic audio premise. This risk cascades: without a rock-solid, deterministic CI gate, regressions in audio behavior (the very thing the gate is meant to catch) become undetectable, and the entire audio system becomes a liability instead of a feature. The ADR has placed a **foundational requirement on a property that the chosen engine does not explicitly guarantee.** This is the highest-risk oversight.
