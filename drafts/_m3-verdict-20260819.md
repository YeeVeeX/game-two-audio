## Phase 1 — per_category_caps enforced (commit 41b59ea)

Semantics (pinned in code + tests): category = the cue's **bus**. At cap →
steal WITHIN the category by the same data-driven chain (lowest_priority →
furthest → oldest), even when free slots exist (a cap is a ceiling, not a
reservation); refuse (nil) when the best in-category victim outranks the
incoming. category nil / capless bus / no caps table = M1/M2 global behavior
exactly. Global max still binds on top. Structural consequence documented:
with sum(caps) == max_voices (48+8+8 = 64), a full pool means every category
sits at its cap, so the global steal path is only reachable for capless/nil
categories.

- AudioData validates: cap keys are declared buses, each cap ≥ 1, sum ≤
  max_voices (all three rejection paths unit-tested).
- `replay_cues` trimmed 63 → 47 fillers so sfx sits exactly at its cap at the
  boss event: **the engineered steal keeps the same victim (drone, prio 10)
  at the same frame (168000), now selected by the in-category chain.**
- audio_system_test's two 64-voice fill scenarios re-expressed cap-relative
  (purpose unchanged: steal command order, refuse-and-count). Not a floor
  move: the data always declared 48; M2 simply didn't enforce it.

## Phase 3 — corpus + headroom (commit d1c0ceb)

### Headroom decision (dev of record, KB-informed, pre-approved staging route)

Problem: M2 flagged replay_cues at ~1.3 peak; measured precisely this cycle
pre-staging: **peak 1.1124 (+0.93 dBFS), 4627 samples > 1.0** (47-filler
trim already in). Legal in f32 but clips on any integer/DAC path.

Decision: **data-staged headroom, no limiter in the graph.** sfx bus
volume_db −3 → −10 dB (data/audio/cues.json, dated comment carries the
policy + KB citations: master ceiling −1 dBTP, mix-bus headroom bands —
`music-production/production-fundamentals.md`,
`mastering-and-loudness-standards.md`, `game-audio-pipeline.md`). The
engineered worst case (phase-coherent filler pressure) must sit under
**−1 dBFS sample peak (0.8913)**, pinned by a `peak` expectation on **every**
replay. A limiter would need a custom C node = DLL rebuild = out of M3 scope
by law; nothing in the measurements demanded one (aligned-sum worst cases all
fit under the ceiling with the staging). New ui fixture amp (0.08) budgeted
for its 8-voice coherent sum the same way.

Consequences, measured: worst replay now **−1.76 dBFS** (ui_cap, by design
the corpus's loudest coherent stack), replay_cues **−3.94 dBFS**, over-1.0
**= 0 everywhere**. Bus-gain change shifted every log md5 (expected,
pre-approved); replay_music's WAV sha is byte-identical to M2
(`3691bf40…`) — no sfx voice plays in it, confirming the staging touched
exactly what it should.

One replay-data recalibration with stated reason: replay_cues steal-collapse
`max_ratio` 0.02 → 0.05 — the numerator is the 500 Hz bin's spectral-leakage
floor from the other tones (~0.002 absolute, does NOT scale with the drone),
so the ratio rescaled when the denominator dropped 2.24×; a surviving victim
reads ~1.0 (20× the bound). Collapse measured 0.0211.

### Duck-overlap semantics (AudioSystem change + unit test + rendered replay)

Same-depth overlap during hold = **pure extension**: duck_end moves, **no
fade issued** (one pending fade slot per node — M2 pinned fact 3; a redundant
flat fade would occupy it), single release from update() at the extended
end. Different depth or mid-release re-attack issues from current volume
(beg = −1). Existing single-duck logs unchanged (replay_cues fade sequence
identical to M2's shape). Pinned twice: unit test + replay_duck_overlap's
`group_fade_at count == 4` (attack, extended release, re-attack, final
release — a 5th line = extension re-issued; a missing 4th = re-attack
swallowed).
